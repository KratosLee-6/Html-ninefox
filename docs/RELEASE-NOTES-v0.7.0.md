# v0.7.0 发布说明 · 网页反向拆解

**发布日期**：2026-10-07
**上一版**：v0.6.4（2026-10-06）
**分支**：`main`（默认） · 归档分支：`archive`

---

## 一句话

**把一个真实网页的分区，变成一个结构可编辑的项目。**

之前的版本只能「用一段描述生成一个页面」；v0.7 之后，可以把一个已经存在的页面的
分区结构带进来，正文按许可决定带不带。

---

## 为什么这一版重要

它不是「多了一个页面源类型」，而是**加了一条流水线 + 一套内容承载模型**。

路线图曾写「`intake.py` 已具备约 80% 所需能力」。**重新核实后这句话是错的**：
从抓取到生成，中间那一段是断的——候选的出口只有 approve / components /
motion / style-presets / analyze，**没有一条通向 `composition` 或 `assets`**。

而且不只是缺一条路，是缺的那条路一旦接上就会**静默产出错误结果**：

| intent | 页面正文是否出现 | 修复前的实测 body 字符 |
|---|---|---|
| landing | 0/2 | **0**（完全空白页） |
| archdoc | 0/2 | **26**（只有外壳） |
| dashboard | 0/2 | 291（渲染自己的文案，静默丢弃页面内容） |
| deck | 0/2 | 1187（同上） |
| poster | 0/2 | 115（同上） |
| doc | 2/2 | 204 ✅ |

**而当时全量 526 条测试全绿。** 这是本项目第三次「绿灯但功能是坏的」。

---

## 三个关键取舍

### 一、抽取器质量是通道的瓶颈，不是接线

`extract_components` 原来用平面 `finditer`，`<main>...</main>` 会把内部每个
`<section>` 全部吞掉——而**真实页面绝大多数就是 `<main><section>`**。

于是「拆解」只产出一个巨大的 main 摘要。那不叫拆解，叫摘要。
不改这一处，v0.7 的主体功能等于不存在。

这不是范围蔓延，是必要前提。

### 二、版权按字段判断，而不是按整页

结构、顺序、配色几乎任何页面都能学；**正文不行**。所以规则是按字段的：

| 许可 | 分块携带正文 | 整页进入模板库 |
|---|---|---|
| `open` | ✅ `verbatim` | ✅ |
| `reference` | ❌ `structure_only` | ❌ |
| `inspiration-only` | ❌ `structure_only` | ❌ |

**这一版同时修掉了一个既存矛盾**：此前 `page_blocks_from_candidate` 只允许
`open` 带正文，而批准路径写的是「除 `inspiration-only` 外都放行」——
于是一份 `reference` 许可的页面**一边被判为「只给结构不给正文」，
一边整页 HTML 被原样复制进模板库**。一份意为「可参考、不可照搬」的许可被照搬了。

现在两条路径问同一个函数。

### 三、携带页面正文必须由用户决定

`POST /api/intake/page-blocks` **只读不写**——它返回分区，但不写回候选。
让抓取自动把别人的正文塞进项目，应该是用户的决定，不是抓取的副作用。

## 验证

| 项 | 结果 |
|---|---|
| 全量回归 | **589 passed / 2 skipped**（68 个测试文件） |
| 浏览器端到端 | **22/22** |
| 变异脚本 | **15 个，全部 CAUGHT** |
| CI | **10 个 job，全绿** |

新增的 5 组测试（67 条）里，有两条是这一版特有的：

**一、页面分区必须到达每一个 intent** —— 用**计数**而不是存在性：

```python
assert body.count(ALPHA) == 1   # 不是 assert ALPHA in body
```

只断言存在的话，重复渲染两次照样通过。同时双向断言「该出现的出现」与
「不该出现的没出现」——只查前者抓不到「渲染了全部内容」的漂移，
只查后者抓不到内容丢失。

**二、许可规则必须是同一条** —— 断言两条路径的**答案相同**，而不是各自断言。
这样将来加第四档许可时会暴露分歧，而不是把两份拷贝一起放宽。

---

## 一条必须说清的限制

`extract_components` 的 `text_head` 是**分区可见文本的前 160 字**，不是那个分区的
完整正文。它同样受 `open` 许可约束——非 `open` 一律空。

---

## 明确不在这一版范围内

- **跟随外部样式表**（`<link rel="stylesheet">`）。抓 CSS 会显著放大 SSRF
  暴露面，必须单独设计。
- **图片抽取**。除了版权，还有远程资源可达性、尺寸、占位图的问题。
- **像素级还原**（栅格 / 断点 / 盒模型）。那是另一个产品。
- **合并 `intake.py` 与 `user_gallery.py` 两套抽取器**。是独立的一笔。

## 历史线索：三次「绿灯但功能是坏的」

这条线索比任何单个版本的功能列表都更值得记住。

**v0.6.2** — SSRF 连接级 IP 绑定是正确的安全补丁，但它让**出站抓取 100% 失败**。
发布时 5 个 job 全绿、39 个附件逐个下载重算 SHA-256 全部匹配、元数据门禁通过，
**而功能彻底不可用**。因为那 6 条门禁**全是拒绝型测试**，没有一条让抓取成功
返回过 body：「正确拒绝」与「彻底坏了」信号完全相同。
实证：把实现改回有漏洞的版本，6 条门禁**仍然全绿**。

**v0.6.3** — 用变异测试翻出五条「门禁自己说谎」，其中**三条是作者自己写的门禁
在坏代码上报绿**。同时剔除了一条结构性门禁（变异测试只有 1/5），
留存为 `.rejected` 文件——**一条无效门禁比没有门禁更糟**，它训练人忽略门禁。

**v0.6.4** — 让发布流水线读**发布物本身**：草稿 → 下载 250MB 逐字节回读 → 转正式。

**v0.7.0** — 通道接通，526 条测试全绿，五个生成器产出空白页或丢弃页面内容。

共同点只有一个：**门禁全绿证明的是「没有回归」，不是「功能可用」。**
判断一道门禁有没有用，要问的不是「它会不会红」，而是
「**去掉修复它会不会红**」——所以每一处修复都配一条变异，
且必须真的把修复拆回去看它红。
