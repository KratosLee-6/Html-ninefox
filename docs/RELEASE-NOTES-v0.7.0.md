# v0.7.0 发布说明 · 网页反向拆解

**发布日期**：2026-10-07
**上一版**：v0.6.4（2026-10-06）
**分支**：`main`（默认） · 归档分支：`archive`

---

## 一句话

**把一个真实网页的分区，变成一个结构可编辑的项目。**

之前的版本只能「用一段描述生成一个页面」；v0.7 之后，可以把一个已经存在的页面的
分区结构带进来，正文按许可决定带不带。

---

## 为什么这一版重要

它不是「多了一个页面源类型」，而是**加了一条流水线 + 一套内容承载模型**。

路线图曾写「`intake.py` 已具备约 80% 所需能力」。**重新核实后这句话是错的**：
从抓取到生成，中间那一段是断的——候选的出口只有 approve / components /
motion / style-presets / analyze，**没有一条通向 `composition` 或 `assets`**。

而且不只是缺一条路，是缺的那条路一旦接上就会**静默产出错误结果**：

| intent | 页面正文是否出现 | 修复前的实测 body 字符 |
|---|---|---|
| landing | 0/2 | **0**（完全空白页） |
| archdoc | 0/2 | **26**（只有外壳） |
| dashboard | 0/2 | 291（渲染自己的文案，静默丢弃页面内容） |
| deck | 0/2 | 1187（同上） |
| poster | 0/2 | 115（同上） |
| doc | 2/2 | 204 ✅ |

**而当时全量 526 条测试全绿。** 这是本项目第三次「绿灯但功能是坏的」。

---

## 发布前实测又翻出三个缺陷（真实数据才看得见）

发布验收不用夹具、按真实形状走全链路（本地起真实页面 → 真实抓取
`example.com` → 拆块 → 六类 intent 逐个生成 → 逐字符数数），又翻出三个：

| # | 缺陷 | 为什么全绿看不见 |
|---|---|---|
| 1 | **生产形态的抓取每次成功都崩**：`_api_intake_fetch` 只传 headers，`fetch_reference` 的 `resolver` 留在 `None`，取回成功后的重绑定检查把 `None` 当函数调用——`TypeError`。**自 v0.6 抓取地基起，随 v0.6.2 / v0.6.3 / v0.6.4 三次发布出门** | `test_design_intake.py` 里其余每条用例都**显式注入 resolver**，全绿 |
| 2 | **真实端点产出的分块，每段正文在六个 intent 里渲染两遍**：`heading` 与 `content` 是同一串 `text_head`，渲染器把 heading 放 `<h2>`、content 放 `<p>` | 「恰好一次」门禁的手工夹具 heading ≠ content——夹具证明了自己，没证明端点 |
| 3 | **section 直接嵌套 section 仍被吞成一个摘要**：非贪婪正则在外层区块内**第一个** `</section>`（内层的闭合）处截断，递归拿到半个标签 | 已修的只是「main 里放平级 section」一种形状；夹具恰好只有那一种 |

三条都已修复，各配「去掉修复必须变红」的门禁：F1（新增变异脚本、接入 CI）、
P7（端到端改用抽取器自己的产物数数）、P1/P4（变异重写后 7/7 CAUGHT）。

**共同点还是那一句：门禁全绿证明的是「没有回归」，不是「功能可用」。**
区别只在于这次连「夹具长得像不像真实数据」也成了被门禁的对象。

## 三个关键取舍

### 一、抽取器质量是通道的瓶颈，不是接线

`extract_components` 原来用平面 `finditer`，`<main>...</main>` 会把内部每个
`<section>` 全部吞掉——而**真实页面绝大多数就是 `<main><section>`**。

于是「拆解」只产出一个巨大的 main 摘要。那不叫拆解，叫摘要。
不改这一处，v0.7 的主体功能等于不存在。

这不是范围蔓延，是必要前提。

### 二、版权按字段判断，而不是按整页

结构、顺序、配色几乎任何页面都能学；**正文不行**。所以规则是按字段的：

| 许可 | 分块携带正文 | 整页进入模板库 |
|---|---|---|
| `open` | ✅ `verbatim` | ✅ |
| `reference` | ❌ `structure_only` | ❌ |
| `inspiration-only` | ❌ `structure_only` | ❌ |

**这一版同时修掉了一个既存矛盾**：此前 `page_blocks_from_candidate` 只允许
`open` 带正文，而批准路径写的是「除 `inspiration-only` 外都放行」——
于是一份 `reference` 许可的页面**一边被判为「只给结构不给正文」，
一边整页 HTML 被原样复制进模板库**。一份意为「可参考、不可照搬」的许可被照搬了。

现在两条路径问同一个函数。

### 三、携带页面正文必须由用户决定

`POST /api/intake/page-blocks` **只读不写**——它返回分区，但不写回候选。
让抓取自动把别人的正文塞进项目，应该是用户的决定，不是抓取的副作用。

## 验证

| 项 | 结果 |
|---|---|
| 全量回归（Windows 本机） | **596 passed / 2 skipped**（68 个测试文件；skip 的两条：一条 symlink 仅 Linux 可跑，一条按内容条件跳过） |
| 全量回归（Linux CI 基线） | 上一提交 **588 passed / 1 skipped**；发布提交以 CI 为准（预期 597 passed / 1 skipped） |
| 浏览器端到端 | **22/22** |
| 变异脚本 | **16 个，全部 CAUGHT**（P1/P4 重写、新增 F1） |
| 真实链路实测 | **15/15**（本地真实页面 → 真实抓取 example.com → 拆块 → 六类 intent 各恰好一次 → 反馈迭代不丢 → reference 许可零正文） |
| CI | Test **9 个 job**，发布提交上必须全绿 |

新增的 5 组测试（67 条）里，有两条是这一版特有的；发布前实测又补了
9 条门禁（端点形状 × 6 intent、嵌套切分、标题/正文拆分、生产形态抓取）
和 1 个变异脚本：

**一、页面分区必须到达每一个 intent** —— 用**计数**而不是存在性：

```python
assert body.count(ALPHA) == 1   # 不是 assert ALPHA in body
```

只断言存在的话，重复渲染两次照样通过。同时双向断言「该出现的出现」与
「不该出现的没出现」——只查前者抓不到「渲染了全部内容」的漂移，
只查后者抓不到内容丢失。

**二、许可规则必须是同一条** —— 断言两条路径的**答案相同**，而不是各自断言。
这样将来加第四档许可时会暴露分歧，而不是把两份拷贝一起放宽。

---

## 一条必须说清的限制

抽取器的切片自带 `text_head`（分区可见文本的前 160 字）与 `snippet`（原始 HTML
前 4000 字）。分块落进项目时，`heading` 取分区自己的标题标签（`_split_heading`），
`content` 取去掉标题后的可见正文（前 2000 字）——不是那个分区的完整正文。
它同样受 `open` 许可约束：非 `open` 一律空。

---

## 明确不在这一版范围内

- **跟随外部样式表**（`<link rel="stylesheet">`）。抓 CSS 会显著放大 SSRF
  暴露面，必须单独设计。
- **图片抽取**。除了版权，还有远程资源可达性、尺寸、占位图的问题。
- **像素级还原**（栅格 / 断点 / 盒模型）。那是另一个产品。
- **合并 `intake.py` 与 `user_gallery.py` 两套抽取器**。是独立的一笔。

## 历史线索：四次「绿灯但功能是坏的」

这条线索比任何单个版本的功能列表都更值得记住。

**v0.6.2** — SSRF 连接级 IP 绑定是正确的安全补丁，但它让**出站抓取 100% 失败**。
发布时 5 个 job 全绿、39 个附件逐个下载重算 SHA-256 全部匹配、元数据门禁通过，
**而功能彻底不可用**。因为那 6 条门禁**全是拒绝型测试**，没有一条让抓取成功
返回过 body：「正确拒绝」与「彻底坏了」信号完全相同。
实证：把实现改回有漏洞的版本，6 条门禁**仍然全绿**。

**v0.6.3** — 用变异测试翻出五条「门禁自己说谎」，其中**三条是作者自己写的门禁
在坏代码上报绿**。同时剔除了一条结构性门禁（变异测试只有 1/5），
留存为 `.rejected` 文件——**一条无效门禁比没有门禁更糟**，它训练人忽略门禁。
**但 v0.6.2 的修复没有修尽**：v0.6.3 修了让请求发不出去的三处，
第四处（取回成功后重绑定检查里的 `resolver=None`）让每一次**成功**的抓取
在成功的瞬间崩掉，又在 v0.6.3 与 v0.6.4 的全绿里活过了两次发布。

**v0.6.4** — 让发布流水线读**发布物本身**：草稿 → 下载 250MB 逐字节回读 → 转正式。

**v0.7.0** — 通道接通，526 条测试全绿，五个生成器产出空白页或丢弃页面内容；
发布前实测又翻出三个（生产形态抓取必崩、真实端点分块双重渲染、
嵌套分区吞并），全部修复并各配变异（见上文）。

共同点只有一个：**门禁全绿证明的是「没有回归」，不是「功能可用」。**
判断一道门禁有没有用，要问的不是「它会不会红」，而是
「**去掉修复它会不会红**」——所以每一处修复都配一条变异，
且必须真的把修复拆回去看它红。第四次的教训再进一层：
**门禁喂的夹具也得像真实数据**——「恰好一次」的门禁挡住了重复渲染，
却被自己端点的 heading == content 形状绕过；按生产形态调用一次，
胜过按夹具形态调用一百次。
