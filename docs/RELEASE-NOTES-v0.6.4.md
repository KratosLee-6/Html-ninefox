# Release Notes · v0.6.4

> **状态：门禁收口版 · 2026-10-06**
> 本版本**不新增用户可见功能**。它做的是把「绿灯」这件事变成可信的，并修掉两处
> 因此暴露出来的真实缺陷。
> 若只想拿功能，建议直接用 **v0.6.3**；本版本对 v0.6.3 是纯加固。

---

## 一句话说清这一版

**从 v0.6.0 起，这个仓库有过两次「所有门禁全绿、东西却是坏的」**：
v0.6.0 的便携包过了四个构建 job 与全部测试，装完一启动就崩；v0.6.2 带着
三处阻断缺陷发布，**每一次出站抓取都抛 TypeError**，功能 100% 失败。

v0.6.4 用同一套办法处理它们，并且**这次把发布物本身也纳入门禁**。

## 一、修了两个用户可见的 bug

### 1. 页面配色从来没有到达生成的页面

从 intake 导入一个页面作为风格预设，用户会：

- **预览**里看到页面自己的配色 ✅
- **点生成**，产物里是**默认预设的配色** ❌

全程没有任何报错。原因是两处缺陷叠加：

| # | 缺陷 | 位置 |
|---|---|---|
| 1 | 生成路径用 `_tokens.get_preset(template)` 解析模板，而那是**内置表查找加静默回落**；用户模板不在表里。而**同一个文件里 20 行外的预览路径正确处理了用户模板** | `pipeline.py` |
| 2 | `build_style_preset` 产出 `colors` / `fonts`，**根本没有 `tokens` 键**；而每个消费方读的都是 `tokens`。页面的配色躺在**两个没人读的键**下面，连预览都拿不到 | `intake.py` |

**这个 bug 的成因值得记下来**：`build_style_preset` 确实存在、`preset_id` 确实
进了生成、`preview` 路径确实处理用户模板——**三个环节各自看着都对，接起来是断的**。

顺带修了角色归因：原来按 **CSS 里的文档顺序**取色，所以一个 CSS 里先写白色
背景、黑色正文的页面会得到**白色的「品牌色」**。现在按色度与亮度归因，
并把页面声明的字体分成 display / body 两档。

### 2. `composition["blocks"]` 会把结构化分块压成字符串

一个携带 `{id, kind, heading, content}` 的分块，经过流水线后到达渲染器时
变成了它的 Python repr 字符串。而 `GenerationBlock` 本来就是**为承载任意
JSON 设计的容器**，HTTP 层也原样包装客户端发来的内容——**结构化分块在这个
边界上是合法的，是那个 `str()` 把它毁了**。

现在两种形态都吃得下。这一点是硬约束而不是偏好：`.foxstate.json` 的
`version` 字段**没有读侧**、`load_state` 只校验 `revision`，**没有版本迁移机制**，
而用户手上的 `blocks` 已经是字符串列表——不兼容就是**旧项目静默变空**。

## 二、发布物第一次被真正验证

v0.6.1 / v0.6.2 / v0.6.3 三轮里，两个 103.75MB 的 Linux 附件因带宽限制
**从未真正下载过**，「已验证」实际只意味着元数据对得上。

v0.6.4 起，**发布流水线会自己把每个可安装产物下载回来核对字节**：

```
publish-draft          建「草稿」发布并上传附件（用户看不见）
verify-release-assets  把每个产物回读一遍：字节 / 归档完整性 / 前端载荷
publish-finalize       只有上一步绿了才转正式发布
```

**草稿是全部关键。** 验证必须从发布页下载，而发布必须先存在——所以
「发完再验」验的是一个用户已经看得见的东西。草稿不可见，意味着**坏包从来没出过门**。

代价说清楚：若验证因网络抖动而非真缺陷失败，发布会**卡在草稿**，需要人工确认后
重跑或删掉。这比悄悄发出去一个坏包便宜——v0.6.2 就是「悄悄发出去」的典型。

补充一条静态门禁（`tests/test_release_asset_metadata.py`，12 条）：
每个可安装附件必须有配套摘要、摘要必须是真 sha256、附件名必须带本版本号、
**带着可安装产物的发布不能还是草稿或预发布**（v0.6.2 就是这样出去的）。

### v0.6.3 的六个产物，现已全部按字节核对过

| 产物 | 结果 |
|---|---|
| `htmlninefox-0.6.3-py3-none-any.whl` | 摘要一致，22 个静态文件 + 12 个脚本齐全 |
| `HtmlNineFox-Windows-x64-0.6.3.zip` | 摘要一致，**且真实启动成功** |
| `HtmlNineFox-Setup-0.6.3.exe` | 摘要一致 |
| `HtmlNineFox-macOS-arm64-0.6.3.zip` | 摘要一致，22 个静态文件齐全 |
| `HtmlNineFox-Linux-0.6.3.tar.gz` | 摘要一致（**前三轮都超时的那一个**） |
| `HtmlNineFox-Linux-0.6.3.run` | 摘要一致（108.8MB AppImage） |

**Windows 便携包能启动**这一条最要紧——v0.6.0 的事故形状正是「构建全绿、装完一启动就崩」。

## 三、两条本该早就红却一直没红的门禁

### 1. 一条安全门禁在 CI 上一次都没跑过

`tests/test_ssrf_tls_pinning.py` 依赖 `cryptography`，而该依赖**从未声明**。
v0.6.3 加进去之后，它在每一次 CI 上都以 `ModuleNotFoundError` 死在 setup——
**本机全绿是因为这台机器恰好装了 cryptography 48**。

已修法是**补依赖声明**，不是加 `importorskip`。那条测试的 docstring 本来就
写明它故意不 skip——**skip 就是绿灯**，而那是一条安全门禁。

### 2. 一份证书会在一天后自己过期

同一条测试把自签证书缓存在 `tests/cert/`，有效期 **±1 天**，而只在文件不存在时
重新生成。于是它从第一次运行起 24 小时后就开始失败，报的还是
`CERTIFICATE_VERIFY_FAILED: certificate has expired`——**读起来像产品或网络问题，
实际是夹具腐坏**。现在剩不到一天就重签，窗口给到一年。

## 五、C7：前端共享内核（两步已完成）

调查推翻了计划里两个前提，**范围比原估小一半**：13 个脚本里**只有 2 个**是裸的
（`fox-core.js` 与 `workbench-features.js`），其余 11 个已是箭头 IIFE。

**第一步**把 81,375 字符的内核从 `index.html` 抽成独立文件。真正的根因不是文件
太大，是 `STATIC_FILES` 是**手写白名单**——新脚本不登记就 404，页面全白而所有
门禁全绿。

**第二步**清空了扩展层的 13 行顶层语句（DOM 绑定 + 改内核 `PALETTE`），由内核
显式装配。收益不是「代码变整齐」，是那 6 个纯函数**第一次可以单测**，
以及 `index.html` 的**加载顺序不再是硬约束**。

> 设计阶段有一处判断被实现推翻并订正：曾以为「样式那一半已经有桥」，
> 实测发现桥是断的（见上文 bug 1）。**引用「某条链路已经存在」之前要真的跑通
> 一次并读产物，而不是顺着调用链读代码。**

## 六、v0.7（网页反向拆解）的地基

原路线图写着「`intake.py` 已具备约 80% 所需能力」，**那张表的每个行号都指向
本仓库中不存在的版本**。重新核实后，真实比例大约是**抓取那一半接近完整，
拆解那一半基本不存在**。

v0.6.4 打好了地基，**不含该功能本身**：

- 页面分块**能穿过流水线**并被 `doc.py` 渲染
- 页面的配色与字体**能到达产物**
- 词表副本**不会静默漂移**

仍未做：把 intake 已有的 section 切片接上去；版权的**字段级**过滤
（现有规则是整页级的二元判断）；5 个其余 intent 学会消费分块通道。
