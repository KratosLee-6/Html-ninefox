# 硬骨头 · 设计：让门禁能看见「功能真的能用」

> 建立时间：2026-10-04
> 基线：`v0.6.3` → commit `b7237be`
> 状态：**已实现，变异验证 9/9 全部捕获**

---

## 一、问题的真实形状

三次事故，同一个洞：

| 版本 | 发生了什么 | 流水线怎么说 |
|---|---|---|
| v0.6.0 | Windows 便携包**一启动就崩** | 四个构建 job 全绿、全部测试通过 |
| v0.6.2 | 出站抓取 **100% 失败**，每次抛 `TypeError` | 五个 job 全绿、39 个附件逐个下载重算 SHA-256 全过、元数据门禁通过 |
| v0.6.2 | 六条门禁全是拒绝型 | 把实现改回漏洞版本，**六条仍然全绿** |

共同根因不是「测试写得不够多」，而是**测试只能观察到「拒绝」，观察不到「成功」**。

当一个套件里每条用例的形式都是「输入坏东西 → 断言被拒绝」，
那么「实现正确所以拒绝」和「实现彻底坏了所以报错」在套件眼里**是同一个信号**。

**「构建成功」与「功能可用」是两个命题，而流水线只验证了前一个。**

## 二、两条走错的路（记录下来，避免重蹈）

### 2.1 扫描源码文本

第一版门禁检查「workflow 里含不含 `verify_portable.py`」「测试文件里含不含
某个 assert 字符串」。变异测试 **1/5**——五种真实破坏下有四种照样全绿。

原因：它验证的是**文本形状**，不是行为。一行注释就能满足
`assert "某串" in read_text()`。

**判据**：如果一条门禁只是「某段文本出现在某处」，它就不是门禁。

### 2.2 逐模块推断覆盖率

第二版试图自动推断「每个模块是否有能观察成功的测试」，结果报出 30+ 个模块
未覆盖，包括 `pipeline`、`recipe_run` 和全部 `generators/*`——而这些模块
都有大量测试。**一条会对三十个模块误报的门禁比没有门禁更糟**，它训练人忽略门禁。

**已剔除**，留存于 `tests/test_gate_quality_gates.py.rejected`（未提交）。

## 三、解法：执行真实代码，断言真实产物

`tests/test_smoke_success_paths.py`，14 条，全部遵循两条纪律：

1. **不扫描文本**——没有任何一条断言「某字符串在源码里」，全部跑代码；
2. **不提前跳过**——观测不到就失败，因为跳过会被读成通过。

覆盖：

| 路径 | 断言的是产物 |
|---|---|
| 六个生成器 × 完整文档 | doctype、闭合标签、token CSS、语言声明、长度下限 |
| 生成器嵌入 brief | 产物里必须出现 brief 的真实文案 |
| 风格预设生效 | 两个预设的产物必须不同 |
| 导出分析 | `source_size` 与磁盘字节一致、`intent` 从项目状态读出、runtime 报告格式 |
| **真实 PDF 导出** | `%PDF-` 魔数、体积 >1KB、结尾有 `%%EOF` |
| **intake 传输层** | 真实 socket 取回字节，与页面逐字节相同 |
| intake 解析 | 标题、heading 列表、语义标签统计、颜色/字体令牌 |
| SSRF 拒绝 | 私网地址必须被拒 |
| 打包验证器接线 | `verify_portable.py` 存在且接进了 workflow |

## 四、判定标准：变异测试

**「14 条全过」不能作为提交依据。** 判据是：
故意破坏生产实现，门禁必须变红。

`scripts/mutate_smoke_gates.py` 逐一破坏九处真实代码：

| # | 破坏方式 | 结果 |
|---|---|---|
| M1 | landing 页面不闭合 `</html>` | CAUGHT |
| M2 | 生成器丢掉 token CSS 块 | CAUGHT |
| M3 | landing 生成器直接返回空壳 | CAUGHT |
| M4 | 分析器谎报 `source_size` | CAUGHT |
| M5 | 分析器写死兼容性分数 | CAUGHT |
| M6 | 骨架解析器丢掉标题 | CAUGHT |
| M7 | SSRF 私网守卫被关 | CAUGHT |
| M8 | 运行时谎报支持 pdf | CAUGHT |
| **M9** | **出站抓取每次都失败（v0.6.2 的真实形状）** | **CAUGHT** |

**9/9 全部捕获。**

M9 是这套门禁存在的全部理由——它是 v0.6.2 实际发生的事。
**第一版 smoke 抓不到它**：那时 intake 只测了「字节到达之后的解析」，
没测传输本身。加上 `test_intake_transport_returns_real_bytes_over_a_real_socket`
之后才抓住。

> 这和我在 SSRF 门禁上犯的错是同一类：**只测了自己想到的部分，
> 没有覆盖事故的真实形态**。是 M9 变异把缺口照出来的。

## 五、写 smoke 时踩到的四个真实错误

它们本身就是这套门禁有效的证据——每一条都是在「以为能跑」时被它挡下的。

| # | 我犯的错 | 它暴露的事实 |
|---|---|---|
| 1 | brief 内容放顶层，实际在 `brief["content"]` 子字典 | 断言对着内置默认值「通过」了——**在测自己的 fixture** |
| 2 | preset 名写 `shadcn`，实际是 `shadcn-dashboard` | 凭想象写的契约 |
| 3 | parser 属性写 `sections`，实际是 `headings`/`semantic`/`title` | 同上 |
| 4 | 用 `Path.write_text` 造数据，断言 `source_size == len(html.encode())`，差 211 字节 | **`write_text` 在 Windows 上做 CRLF 转换，而产品的 `durable.atomic_write` 用 `newline=""` 禁用了它**。改用产品自己的写入函数才对上 |

第 4 条尤其值得记：它让我一度以为产品有 bug，实际是**我的测试数据用了和产��不同的写入方式**。

## 六、CI 接入

`test.yml` 新增独立 job `smoke-success-paths`：

1. 跑 smoke 套件；
2. **再跑变异验证**——每个生产路径被故意破坏，门禁必须变红。

单独成 job 的理由：它比主套件慢（复制工作树、跑九次），
但它是**唯一能证明门禁本身有效**的检查。若变异步骤某天抓不到东西，
这个 job 会红——那正是它存在的意义。

失败时上传 `/tmp/htmlninefox-mutation/` 下的工作树。
放系统临时目录而非仓库内：`.codex_tmp/` 与 `.tmp/` 都在 `.gitignore` 里，
证据从那里永远传不上来。

## 七、这条方案解决了什么、没解决什么

**解决了**：v0.6.0 / v0.6.2 那一类事故——「流水线全绿而功能坏了」。
现在这类问题会在 CI 里变红，且有变异测试证明它真的会红。

**没解决**：

- 覆盖的是当前已识别的关键路径。**新增功能时若不同时加 smoke，缺口照旧**——
  这个门禁不强制新功能必须配 smoke，那需要另一套「改动清单 ↔ smoke 覆盖」的对账机制。
- 没有覆盖 UI 层。两个版本的 bug（导出中心没有 PPTX 选项、幻灯片竞态）都在前端，
  而前端目前**无法被单元测试**（C7：12 个 classic script 共享顶层作用域）。
  这是下一个该啃的骨头。
