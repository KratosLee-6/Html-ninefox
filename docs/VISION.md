# VISION · 人机共驾的内容交付流水线

> 做这个应用的根本：**把整条线路串联起来——AI 方便工作对接的同时，
> 人也能清晰查看和调整。** 本文是产品的北极星陈述，也是每个版本
> 规划（见 PLAN-*.md）的立项标尺。

---

## 1. 一句话

Html九尾狐是一条**人机共驾**的内容交付流水线：AI 负责重活（理解、拆解、
生成、改写），人负责判断（审核、调整、采纳、交付）。每一个 AI 阶段的
输出都是一个**交接产物（artifact）**——机器可读、人可审核、可改了再往下走。

## 2. 整条链路与它的交接面

```text
输入                 理解                拆解               生成              迭代            交付
URL/ZIP/DOCX/口述 → 候选(审核台)     → blocks+provenance → 六类产物+风格   → 口语反馈      → PPTX/PDF/
文件/图片           大纲+提案          +设计令牌           (离线引擎/LLM)    revision 历史    PNG/DOCX/HTML
                    【人：审核/改】     【人：选用/覆盖】    【人：画布调整】  【人：对比/恢复】 【人：导出中心】
```

**串联的判据**：相邻两个阶段之间，交接产物必须有双重形态——
结构化数据（API 可驱动，外部 AI agent 能接管）+ 界面呈现（人能看见、
能改）。只有其一，就是断链。

## 3. 现状对照（v0.7.8 时点）

| 交接面 | 机器形态 | 人的形态 | 状态 |
|---|---|---|---|
| 输入 → 理解 | CandidateStore（evidence/candidate.json） | 审核台（采纳/拒绝/预览） | ✅（URL/ZIP）|
| 理解 → 拆解 | `page_blocks`（blocks + provenance 三档） | 审核台拆块预览 | ✅ v0.7 |
| 拆解 → 生成 | composition.blocks / style.tokens | 画布节点 + 素材库 + 风格面板 | ✅ |
| 生成 → 迭代 | revision 历史（expected_revision 写回协议） | 版本差异对比 + 恢复 | ✅ |
| 全程 | recipe_run 时间线 | 阶段时间线 UI | ✅ |
| 生成 → 交付 | exporting（pptx/pdf/png/…） | 导出中心 | ✅（DOCX 导出进行中）|
| **输入：DOCX** | ✗ | ✗ | **缺口（v0.8.1）** |
| **视觉：图片环节** | ✗（无提案产物） | ✗ | **缺口（v0.8.1）** |

## 4. 三条不变的原则

1. **交接产物原则**：新功能必须回答「它的交接产物是什么、人在哪里看、
   在哪里改」。答不出这三问的功能不立项。
2. **LLM 是升级不是依赖**：每个 AI 环节都有离线兜底（规则引擎/占位符），
   未配置 Key 时功能不缺失、只降级，且降级方式如实呈现。
3. **本地优先**：内容、密钥、产物不出本机；对外请求只发生在用户明确
   配置的模型与抓取动作上。

## 5. 这个北极星如何约束版本规划

- v0.8.1 的「DOCX 导入 + AI 理解补全」就是缺口的直接补位：AI 理解文档
  产出**提案产物**（意图/风格/图片计划/提炼文案），全部落进审核台由人
  编辑采纳——而不是黑盒直出。
- 「图片环节」的补法遵守原则 2：AI 先产出图片计划（slot + 提示词 +
  占位），图像模型的接入（哪家、成本）是配置项决策点，不是功能前提。
- 外部 agent 驱动：管线已有 HTTP seam 与 recipe run 审计，后续按需补
  全程驱动的 API 面（alliance 联盟是该方向的既有雏形）。
