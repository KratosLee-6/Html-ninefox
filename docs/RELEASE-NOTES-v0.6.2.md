## 风险口径（请先读这一段）

**这不是一个新发现的漏洞，而是关闭一个已经公开披露过的残余风险。**

- 披露时点：`v0.6.0` 发布说明的「许可与来源治理」章节，已将「SSRF 连接级 IP 绑定未完成」列为已知残余风险。
- 披露后到本版之间，风险的实际暴露面是 **12 个内置设计源**——地址由产品内置、用户不能自由输入。
- 本版把它提前关掉，而不是等到 v0.7。原因是 v0.7 要做「粘贴任意网址 → 拆解」，那条入口会让暴露面从 12 个已知地址变成**任意地址**。拿新功能去赌一个已知残余风险，顺序是错的。

### 缺陷本身

`fetch_reference` 从 `validate_url` 拿到已校验的 IP 列表，**但从未把它传给传输层**；
而 `_default_transport` 交给 `urllib` 建连时，`urllib` 会**自己再解析一次 DNS**。
两次解析之间存在一个时间差：

```text
t0  validate_url()  →  解析得公网地址，校验通过
t1  urllib 建连     →  再解析，得 127.0.0.1，连上了私网
t2  响应到达        →  重新解析比对，发现变了 → 丢弃响应
```

原来的第 3 步是**事后检测**，不是**事前防护**：响应确实会被丢弃，
但**字节已经通过那条通往私网的连接流进了内存**，而这段字节可能落入落盘的证据目录。

> 模块顶部的 docstring 原先写作「so DNS rebinding cannot swap in a private
> target mid-flight」——**这句话当时不准确**。它做到的是「发现后丢弃」，
> 不是「不能被换掉」。本版已改为如实描述。

## 修复

- 新增 `_PinnedHTTPHandler` / `_PinnedHTTPSHandler`：**socket 连到已校验的地址**，
  `Host` 头与 TLS 的 SNI、证书校验仍使用真实主机名。因此虚拟主机站点不受影响，
  证书校验也没有被削弱。
- 重定向**逐跳独立校验并绑定**——第 N 跳不复用第 N−1 跳的地址。
- 保留响应后的重新解析比对，作为纵深防御的第三层（绑定 → 连接即校验 → 事后检测）。
- 失败路径返回稳定错误码 `intake_connect_failed`，不退化成 500。

## 验证

- **新增 6 条门禁**（`tests/test_ssrf_connection_pinning.py`），全部走**真实 socket**：
  起一个真实 `http.server` 监听 127.0.0.1，用脚本化 resolver 让它先返回公网、
  再返回 127.0.0.1（即攻击者的真实手法），断言请求必须**因决策而失败**。
- **反向验证**：摘掉绑定逻辑 → 门禁变红，失败信息明确指出「连接被尝试了，不是被阻止」；
  恢复 → 全绿。
- 既有 62 条 intake 测试**全部通过且零放宽**——没有为了让新实现过关而修改任何既有断言。
- 全量测试 **409 passed / 1 skipped**（v0.6.1 为 403）。

> ### 为什么既有测试没抓到（值得记）
>
> `test_design_intake.py` 里连 DNS rebinding 那条在内的**所有** SSRF 测试，
> **都注入假 transport**。它们验证的是「校验逻辑还在跑」「解析结果变了会被发现」，
> **没有一条验证真实连接连到了哪个 IP**。只要 `validate_url` 还在跑，任何实现都能全绿。
>
> 门禁本身也踩过同一个坑：第一版用「固定返回公网」的 resolver，跑出来是**绿的**——
> 因为 `urllib` 连的是公网地址，压根够不到本机服务，什么都没证明。
> 门禁第一版还有一处 `assert SECRET not in str(exc)`（bytes 比 str）抛 TypeError，
> 意味着「私网字节没进内存」这条**根本没被执行**。
>
> 三者都是「看起来在测、其实没测到」的同一形状。

设计文档见 [`DESIGN-v0.6.2-ssrf-pinning.md`](DESIGN-v0.6.2-ssrf-pinning.md)，
含实现过程中撞到的三处 API 契约陷阱（`urllib` 的 `do_open` 签名、`Request` 无 `.port`、
HTTPS 不能与 HTTP 共用 helper）。
